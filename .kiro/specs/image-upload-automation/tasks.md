  - アップロード要求に画像アップロードの承認フラグを、実行前確認情報に画像計画を、実行履歴に画像の集計と作業用下書きURLを追加する

- [x] 2. コア部品: 本文の置換・対応表・設定・ブラウザ操作
- [x] 2.1 (P) 画像参照の抽出と置換を純粋関数として実装する
  - Markdown画像記法とimgタグからローカル画像参照を出現順・重複なしで抽出し、外部URL・`//`・`#` 始まりとコードブロック内を除外する
  - 対応表に従ってパス部分だけを置換し、代替テキスト・title・imgタグの他の属性を変えない。対応にない参照はそのまま残す
  - 既存のアップロード機能が使っているローカル画像参照の抽出をこの部品へ移し、既存の呼び出し元の挙動を保つ
  - 完了条件: 抽出・除外・置換(属性の保持、空の対応表で本文が不変)の単体テストが成功し、既存のアップロード機能のテストもすべて成功する
  - _Requirements: 2.1, 2.2, 7.1, 7.2_
  - _Boundary: ImageRefRewriter_

- [x] 2.2 (P) 画像とURLの対応表の保存部品を実装する
  - 既存記事は記事の管理情報に、新規記事は記事フォルダ直下の補助ファイルに、対応表を読み書きする
  - 1件記録するたびに一時ファイル経由で書き込み、同じ内容ハッシュのエントリは1件にまとめて参照パスを追加する。エントリは削除しない
  - バックアップフォルダ内の全記事から同じ内容の画像を探せるようにする
  - 完了条件: 保存先の振り分け、同一ハッシュの統合、記事をまたいだ検索、書き込み途中の失敗で既存の記録が壊れないことの単体テストが成功する
  - _Requirements: 7.4, 7.6, 7.7, 8.2_
  - _Boundary: ImageMapStore_

- [x] 2.3 (P) 記事の保存処理が対応表を失わないようにする
  - 記事の保存(バックアップと更新アップロードの両方)で、既存の管理情報にある対応表をそのまま引き継ぐ
  - 新規記事の登録後のフォルダ変換で、補助ファイルの対応表を新しい管理情報へ移し、管理情報の書き込みに成功した場合だけ補助ファイルを削除する(削除は `unlinkSync` を使う)
  - 閲覧用Markdownは利用者が書いた相対参照のまま保存する
  - 完了条件: バックアップ後も対応表が残ること、フォルダ変換後に対応表が引き継がれ補助ファイルが消えること、管理情報の書き込み失敗時は補助ファイルが残ることの単体テストが成功する
  - _Requirements: 7.3, 7.5_
  - _Boundary: StorageManager_

- [x] 2.4 (P) 画像アップロード機能の設定保存部品を実装する
  - 有効化・同意日時・セッション保存の有無・作業用下書きURLを専用フォルダの設定ファイルに保存する。ファイルがなければ「無効」を既定とする
  - 同意が記録されていない状態での有効化を拒否する
  - 保存済みのブラウザプロファイルを削除し、セッション保存を無効に戻す手段と、保存済みかどうかの判定を提供する
  - 完了条件: 既定値、同意なしの有効化拒否、作業用下書きURLの記録、セッション削除の単体テストが成功する
  - _Requirements: 1.1, 1.4, 5.1, 5.2, 5.3, 9.1_
  - _Boundary: ImageUploadSettingsStore_

- [x] 2.5 (P) Qiitaエディタの画面定義とブラウザの起動・終了を実装する
  - エディタのURL、画像投入欄と本文エディタの要素、Qiitaのドメイン判定、画像配信ホストの許可判定、受け付ける形式と容量上限を1か所の画面定義にまとめる(2026-10-25 の観測内容を根拠として残す)
  - ブラウザ操作ライブラリを動的に読み込み、読み込めない場合は利用不可の理由を返す
  - 画面ありのブラウザを Edge → Chrome の順に起動し、セッション保存ありなら専用フォルダ、なしなら一時フォルダをプロファイルに使う。終了時は一時フォルダを削除し、何度呼んでも安全にする
  - ツール自身の画面遷移は Qiita のURLに限り、アクセストークンには依存しない
  - 完了条件: ライブラリ未導入時に利用不可が返ること、画面定義の判定(Qiitaドメイン・許可ホスト)、終了処理の多重呼び出しの単体テストが成功する

  - _Boundary: EditorImageUploader, QiitaEditorProfile_

- [x] 2.6 ログイン完了の待機と画像1枚の投入を実装する
  - 作業用下書きの編集画面(なければ新規作成画面)を開き、現在のURLがエディタに一致し画像投入欄が現れるまで待つ。タイムアウト・ブラウザを閉じた・中断を区別して返す
  - 画像1枚ごとに、本文を空にする → 投入前のURL集合を取る → 画像を投入する → 新しい許可ホストのURLが現れるまで待つ → URLを返す → 本文を空にする、の順で処理する
  - 必要な画面要素がなければ、どの要素がないかを示して失敗を返す
  - ID・パスワード欄、保存・投稿・公開のボタン、設定画面には触れず、Cookie・ストレージの値を読まない
  - 自動保存で確定した作業用下書きのURLを取得できるようにする
  - 完了条件: 模擬エディタ画面に対する実ブラウザのテストで、URLの取得と本文が空になることを確認できる(ブラウザがない環境ではスキップされる)
  - _Requirements: 4.2, 4.3, 6.1, 6.2, 6.4, 6.7, 8.1, 9.3_
  - _Depends: 1.3_

- [x] 3. アップロード計画の作成部品を実装する

  - ファイルがない、記事フォルダの外を指す(シンボリックリンク解決後を含む)、形式が対象外、容量上限を超える、をそれぞれ理由付きで判定する
  - 内容ハッシュで対応表を引き、記録済みなら再利用、パスが同じでも内容が変わっていれば再アップロードとする
  - 同じ内容の画像が複数の記事・参照にあっても、送る枚数と合計容量は1回分として数える。ファイルへの書き込みは行わない
  - 完了条件: 欠落・フォルダ外・形式外・容量超過・再利用・内容変更・複数記事での重複の単体テストが成功し、枚数・合計容量・再利用件数が計画に含まれる

- [x] 4. 画像フェーズの統括サービスを実装する
- [x] 4.1 ブラウザのセッションの開始から終了までを統括する
  - 承認された計画で、設定にあるセッション保存の有無と作業用下書きURLを渡してブラウザを開き、ログイン待機の開始を進捗イベントで通知する
  - ログインのタイムアウト・ブラウザを閉じた・待機中の中断・起動失敗を、それぞれ画像フェーズのエラーとして返す
  - 正常・失敗・中断・予期しない例外のどの経路でもブラウザを閉じる
  - 画像フェーズの終了時に作業用下書きURLを設定へ記録する
  - タイムアウトの既定値(ログイン5分・1枚90秒)をオプションで差し替えられるようにする
  - 完了条件: 偽の部品を使った単体テストで、各エラーの返却と、すべての経路でブラウザが閉じられることが確認できる
  - _Requirements: 4.1, 4.3, 4.4, 4.5, 8.5, 9.1, 10.4_

- [x] 4.2 画像の投入・記録・進捗通知を実装する
  - 送る画像を内容ハッシュ単位で1回ずつ投入し、得たURLを参照しているすべての記事の対応表に、得られた時点で記録する
  - 許可ホスト以外のURLや、時間内にURLが得られない画像は失敗として記録し、対応表には書かない
  - 1枚ごとに進捗(処理済み枚数・対象枚数・画像名)と結果を通知し、中断の指示は1枚の区切りで確かめる
  - 画面要素の不在では処理を止め、それまでの結果を添えて返す
  - 記事ごとに「すべての画像のURLが揃った(置換用の対応を含む)」か「失敗した参照の一覧」かを返し、送信・再利用・失敗の件数を集計する
  - 完了条件: 偽の部品を使った単体テストで、重複画像が1回だけ投入されること、失敗した画像が記録されないこと、中断後も成功分が対応表に残ること、記事ごとの結果と件数が正しいことが確認できる
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.5, 6.6, 8.1, 8.2, 8.3_

- [x] 5. 既存のアップロード機能・API・画面への組み込み
- [x] 5.1 実行前確認に画像計画を載せ、承認の有無で分岐する
  - 機能が有効かつ利用可能で、送る必要のある画像がある場合だけ、実行前確認情報に画像計画を付ける。無効なら従来と同じ確認情報を返す
  - 画像アップロードの承認フラグと実行前確認の同意の両方がある場合だけ、画像フェーズを実行対象にする
  - 承認がない場合は、送る必要のある画像の参照を変えずに従来どおり送り、既存のローカル画像警告を維持する
  - 完了条件: 機能無効・承認なしの場合の確認情報と送信本文が従来と同一であること、承認ありの場合に画像計画が返ることの統合テストが成功する
  - _Requirements: 1.2, 3.1, 3.3, 3.4_
  - _Depends: 3, 2.4_

- [x] 5.2 アップロードRunに画像フェーズを差し込み、記事ごとに分岐する
  - 既存のRunの排他の中で、記事の処理より前に画像フェーズを実行する
  - ログインの失敗・ブラウザを閉じた・中断・起動失敗・予期しないエラーでは、記事アップロードを1件も行わない
  - 画面要素の不在では、新しい画像が不要な記事だけ記事アップロードを続ける。画像が1枚でも失敗した記事は送らずに失敗として記録し、他の記事は続ける
  - 送信本文だけを対応表で置換し、閲覧用Markdownには書き戻さない
  - 結果サマリと実行履歴に、画像の送信・再利用・失敗の件数、失敗した画像と理由、作業用下書きURL、画像フェーズの中止理由を載せ、どの終了経路でも管理情報の保存とGitコミットを行う
  - 完了条件: 偽の部品とモックQiitaサーバを使った統合テストで、置換された本文が登録・更新の要求に渡り、閲覧用Markdownが変わらず、各失敗パターンで送られる記事・送られない記事が仕様どおりになる

  - サーバの組み立てで新しい部品を接続し、ブラウザ操作部品にアクセストークンを渡さない。待ち受けはループバックのみのまま保つ
  - 完了条件: API単位のテストで、取得・同意付き有効化・同意なしの拒否・セッション削除・実行中の拒否・承認フラグの受け渡しが確認できる
