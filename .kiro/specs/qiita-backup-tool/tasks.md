# Implementation Plan

- [x] 1. 基盤: プロジェクトセットアップとサーバ骨格
- [x] 1.1 Node.js+TypeScriptプロジェクトの初期化とローカルサーバ起動基盤を構築する
  - パッケージ定義・TypeScript(strict)・ビルド設定を作成し、フロント静的アセットの配信を含むExpressサーバを用意する
  - サーバはループバックアドレスのみで待ち受け、起動時にアクセスURLをコンソールへ表示する
  - ファイルへの実行ログ出力(時刻・レベル・コンテキスト付き)を組み込み、トークン等の秘匿情報を出力しない方針をログ基盤に組み込む
  - ツール本体リポジトリ用の `.gitignore`(.env / backups / logs 等)と値なしの `.env.example` を同梱する
  - 観測可能な完了条件: 単一コマンドで起動し、ブラウザで `http://localhost:{port}` からプレースホルダ画面が表示され、ログファイルが生成される(Windows 11上で確認)
  - _Requirements: 7.1, 8.3, 8.4, 10.1, 10.2, 10.3_

- [x] 1.2 設定読み込みとアクセストークン管理の基盤を実装する
  - `.env` からトークン・バックアップ先・ポートを読み込み、トークンはメモリ上で一元保持する
  - トークンのマスク表示(末尾4桁のみ)を提供し、全文が画面・ログへ出ない契約にする
  - ユーザ同意時のみ `.env` のトークン行だけを置換/追記し、他のキー・コメントを保持する更新処理を実装する(ファイル未存在時は新規作成)
  - 観測可能な完了条件: 既存キーを含む `.env` に対しトークン行のみが更新されることを検証するユニットテストが通る
  - _Requirements: 1.1, 1.6, 1.7, 8.1, 8.2_

- [x] 2. インフラ層: 外部リソースアクセス
- [x] 2.1 (P) Qiita APIクライアントを実装する
  - トークン検証(認証中ユーザ取得)でユーザIDと投稿記事数を返し、401/403/429/ネットワーク/サーバエラーを型で区別する
  - 記事一覧をページング追跡(1ページ100件、次ページリンクの追跡)で全件取得し、限定共有記事を含むメタデータと本文を返す
  - レート制限ヘッダを監視し、429受信時は再開可能時刻を呼び出し元へ返す。認証ヘッダはQiita APIへのリクエストにのみ付与する
  - 観測可能な完了条件: モックHTTPサーバに対し、複数ページの全件取得と429時の再開時刻返却を検証するユニットテストが通る
  - _Requirements: 1.2, 2.1, 3.12, 8.1_
  - _Boundary: QiitaApiClient_

- [x] 2.2 (P) 画像ダウンローダを実装する
  - Markdown本文から画像参照(Markdown記法とimgタグの両方)を重複なく抽出する
  - 認証ヘッダを一切付けない独立したHTTPアクセスで画像を直列(間隔付き)ダウンロードする
  - ファイル名は登場順連番+元ファイル名(ファイル名相当がないプロキシURLは連番のみ)とし、拡張子はレスポンスのContent-Typeから決定する
  - 失敗した画像は理由付きで記録し、処理全体は継続する
  - 観測可能な完了条件: Camo形式URL・同一URL複数参照・失敗混在のケースを含む抽出/命名/継続のユニットテストが通る
  - _Requirements: 3.5, 3.8, 4.4, 8.5_
  - _Boundary: ImageDownloader_

- [x] 2.3 (P) 記事ストレージ管理を実装する
  - バックアップ先ルート(設定で変更可)を自動作成し、記事ごとに「サニタイズ済みタイトル(最大50文字)+記事ID」のフォルダを作成する
  - 閲覧用Markdown・取得原文(original)・記事メタ情報(反応数・画像結果含む)・imagesサブフォルダを規定の構成で保存し、再バックアップ時は上書きする
  - 記事IDが一致しフォルダ名が変わる場合は既存フォルダをリネームする
  - JSONの書き込みは一時ファイル経由のアトミック方式とし、バックアップ先外への書き込みを拒否する
  - 記事フォルダをOSのエクスプローラで開く操作を提供する
  - 観測可能な完了条件: 禁止文字・長文タイトル・タイトル変更リネーム・アトミック書込(中断シミュレーション)のユニットテストが通り、保存後のフォルダ構成が外部要件書4.4の構成図と一致する
  - _Requirements: 2.5, 3.4, 3.7, 3.11, 4.1, 4.2, 4.3, 4.5, 4.6, 9.3_
  - _Boundary: StorageManager_

- [x] 2.4 (P) Git世代管理マネージャを実装する
  - 起動時にGitの可用性を判定し、利用不可なら以後の操作を無害化して警告状態を公開する
  - バックアップフォルダをツール本体と独立したGitリポジトリとして自動初期化する(リモート関連操作は実装しない)
  - Run単位で全変更をステージし、実行日時・対象/成功/失敗件数を含むメッセージでコミットする。変更ゼロならコミットしない。フォルダリネームは履歴追跡可能な形でコミットされる
  - 観測可能な完了条件: 一時ディレクトリ上で「初期化→変更コミット→変更なしスキップ→リネーム追跡」を検証する統合的ユニットテストが通る
  - _Requirements: 6.1, 6.2, 6.4, 6.5, 6.6_
  - _Boundary: GitManager_

- [x] 3. サービス層: 業務ロジック
- [x] 3.1 (P) 接続確認サービスを実装する
  - 設定由来トークンまたは画面入力トークンで接続確認を行い、成功時はユーザIDと投稿記事数を返してメモリ上のトークンを更新する
  - 未設定・無効・権限不足を区別したエラーを返し、発行手順案内の表示に必要な情報を提供する
  - 保存同意ありの場合のみ `.env` へ保存し、同意なしの場合はメモリのみ保持とする
  - 観測可能な完了条件: 有効/無効/未設定トークン×保存同意あり/なしの組み合わせを検証するユニットテストが通る
  - _Requirements: 1.2, 1.3, 1.4, 1.5, 1.6, 1.7_
  - _Boundary: AuthService_
  - _Depends: 1.2, 2.1_

- [x] 3.2 (P) 状態管理ストアを実装する
  - 記事ごとの管理情報(バックアップ日時・Qiita側更新日時・コンテンツハッシュ等)を管理ファイルで永続化し、アトミックに保存する
  - Qiita一覧と管理情報を突合し、5状態(未バックアップ/最新/Qiita側更新あり/ローカル変更あり/Qiita側削除)へ分類した一覧ビューと集計値を返す
  - Qiita側削除の記事のローカルデータは削除しない
  - バックアップ実行履歴(日時・件数・成否・コミット情報)を追記・参照できる
  - 観測可能な完了条件: 設計書の状態分類表の全分岐(境界条件含む)を網羅するユニットテストが通る
  - _Requirements: 2.2, 5.1, 5.2, 5.3, 5.4, 5.6, 5.7, 5.8_
  - _Boundary: StateStore_
  - _Depends: 2.3_

- [x] 3.3 バックアップ実行サービスと進捗イベントを実装する
  - 全件/差分(既定)/選択の3モードでRunを構成し、同時実行は1件に制限する(実行中の開始要求は競合エラー)
  - 記事ごとに本文取得→画像ダウンロード→画像参照の相対パス書き換え→保存→状態更新を行い、進捗イベント(件数・処理中記事・記事完了・レート待機・完了サマリ)を発行する
  - 「ローカル変更あり」記事を含む場合は上書き確認済みフラグを要求する
  - 中断指示は処理中記事の完了を待って停止し、中断・完了のいずれでも管理情報保存とGitコミットを実行する
  - 429時は再開時刻まで待機して自動再開し、ネットワーク/サーバエラーは記事単位で上限付きリトライのうえ失敗記録して継続する
  - 観測可能な完了条件: モック構成で「差分Run一式完了」「中断時の部分保存+コミット」「429待機→再開」を検証する統合テストが通る
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.6, 3.8, 3.9, 3.10, 3.12, 5.5, 6.3, 9.2_
  - _Boundary: BackupService, ProgressBus_
  - _Depends: 2.1, 2.2, 2.3, 2.4, 3.2_

- [x] 4. HTTP APIの実装と配線
  - 接続状態取得/接続確認/記事一覧(再取得オプション付き)/フォルダを開く/バックアップ開始・中断/進捗スナップショット/実行履歴の各エンドポイントを設計書のAPIコントラクト表どおりに実装し、各サービスへ配線する
  - 進捗イベントをSSEストリームとして配信する(再接続時はスナップショットで回復)
  - エラーは統一形式(コード+日本語メッセージ)へ変換する
  - 観測可能な完了条件: curl等で全エンドポイントが仕様どおりのステータス・ペイロードを返し、SSEでRunの進捗イベントが受信できる
  - _Requirements: 1.8, 2.5, 3.9, 5.8, 7.1_
  - _Depends: 3.1, 3.2, 3.3_
