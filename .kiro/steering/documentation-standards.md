# ドキュメント規約

本プロジェクトの文書作成・更新の標準パターン。仕様書ドリブンで進行しているため、
文書間のトレーサビリティ維持が最重要。

## 言語と配置

- 文書は**日本語**で書く(思考は英語でよい。CLAUDE.md の規約に従う)
- 配置ルール:
  - `docs/` — 要件書・設計書などの正式文書
  - `docs/images/` — 文書に埋め込むSVGワイヤーフレーム
  - `research/` — 技術調査報告(実装判断の根拠となる資料)
  - `.kiro/specs/` — Kiro仕様(spec-init以降で使用)

## 版数管理(要件書)

- 文書冒頭のヘッダ表で管理: `| 版数 | 1.6(変更概要) |`
- **内容を変更したら必ず版数をインクリメント**し、括弧内に変更概要を一言で書く
- 決定済みの検討事項は削除せず「(**決定済**)」と記して決定内容と反映版数を残す
  (例: 8章 検討事項#1「Qiita API v2 + トークン方式に決定(v1.2で反映)」)

## 要件ID体系

```
F-{カテゴリ}-{連番2桁}   機能要件   例: F-AUTH-03, F-BK-12
N-{カテゴリ}-{連番2桁}   非機能要件  例: N-SEC-05, N-PERF-02
```

- カテゴリ: AUTH(認証) / LIST(一覧) / BK(バックアップ) / DIR(フォルダ) / ST(状態管理) / GIT(世代管理) / SEC / PERF / OPS
- 新要件は末尾に追番。**既存IDの意味を変えて再利用しない**(削除時は欠番として残す)
- 要件間の参照はID+節番号で書く(例: 「トークン入力欄(F-AUTH-07)」「世代管理(4.7)」)

## SVGワイヤーフレーム規約

- ファイル名: `screen-{連番2桁}-{画面名}.svg`。**画面の内容が変わってもファイル名は変えない**
  (要件書の `<img>` 参照を壊さないため)
- 共通スタイル: ブラウザ窓フレーム+アプリヘッダ(Qiitaグリーン `#55c500`)、
  `font-family="'Segoe UI','Yu Gothic UI','Hiragino Sans',sans-serif"`
- **要件IDアノテーション**: 紫(`#8e44ad`)の小ラベル+破線リーダー線で、画面要素と要件IDを対応付ける
- 条件付き表示の要素は破線枠+「〜の場合のみ表示」ラベルで示す
- 更新後は必ずXML妥当性を検証する:

```powershell
try { [xml](Get-Content $path -Raw -Encoding UTF8) | Out-Null; "OK" } catch { $_.Exception.Message }
```

- 文書には `<img src="images/xxx.svg" alt="..." width="...">` で埋め込む(Markdownリンクではなくimgタグ)

## 要件書とSVGの同期ルール

> 要件を変更したら、対応するSVGのアノテーション・画面要素も同じターンで更新する。
> 逆に、画面に要素を足したら対応する要件(F-xxx)を必ず起こす。片方だけの変更を残さない。

## 調査文書規約(research/)

- 冒頭に調査日・調査目的・**結論サマリ表**を置く(読者は結論から読む)
- 本文は「公式ドキュメントの事実」と「推測・広く報告されている情報」を書き分ける
  (例: レート制限ヘッダ名は公式未記載である旨を明記した上で通説を紹介)
- 末尾に参考資料のリンク一覧を置く
- 要件書へのフィードバック(仕様変更の提案)は調査文書内に独立した章として書き、
  採否はユーザに委ねる(勝手に要件書を変えない)

## 図表

- 処理フローはMermaid(`flowchart`)で要件書内に直接記述
- 表は「短い列挙事実」のみに使い、説明は前後の文章に書く
