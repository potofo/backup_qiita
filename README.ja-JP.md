# Qiita記事バックアップツール

[English](README.md) | 日本語

Qiita API v2(個人用アクセストークン)で自分の全記事(限定共有含む)のMarkdownと画像をローカルへバックアップするローカルWebツールです。状態管理・更新検知と、`backups/` フォルダの独立GitリポジトリによるRun単位の世代管理を行います。

ダウンロード(バックアップ)に加えて、**ローカル→Qiitaのアップロード**にも対応しています。`backups/` 内で新規作成した記事の登録(常に限定共有=非公開)と、ローカルで編集した既存記事の本文更新を、明示的な操作と実行前確認を経て行えます。

## 必要環境

- Windows 11(macOS / Linuxでも動作します)
- Node.js 24 以上
- Git(任意 — 未インストールの場合は世代管理なしで動作します)

## セットアップ

```powershell
npm install
copy .env.example .env   # 任意(トークンは画面からも入力・保存できます)
```

`.env` の設定項目:

| キー | 説明 | 既定値 |
|---|---|---|
| `QIITA_ACCESS_TOKEN` | Qiita個人用アクセストークン(スコープは下記) | (なし) |
| `BACKUP_DIR` | バックアップ先フォルダ | `backups` |
| `SERVER_PORT` | ローカルWebサーバのポート | `3000` |

トークンの発行: Qiitaにサインイン → 設定 → アプリケーション → 個人用アクセストークン → 「新しくトークンを発行する」。

スコープは利用する機能に応じて選びます:

- **バックアップのみ**: `read_qiita`
- **アップロード機能も使う**: `read_qiita` + `write_qiita`

## 起動

```powershell
npm start
```

表示されたURL(既定: `http://localhost:3000`)をブラウザで開きます。サーバはループバックアドレスのみで待ち受けるため、外部からはアクセスできません。

## 使い方

1. **接続確認画面** — トークンの有効性を確認します。未設定・無効の場合は発行手順の案内と入力欄が表示されます(同意した場合のみ `.env` へ保存)。接続バッジには権限種別(読み取りのみ / 読み書き / 未確認)が表示されます。
2. **記事一覧・ダッシュボード** — 全記事を8状態(未バックアップ / 最新 / Qiita更新あり / ローカル変更あり / ローカル新規 / 競合 / ローカル欠落 / Qiita側削除)で表示します。差分(既定)・全件・選択の3モードでバックアップを、「変更点をアップロード」「選択をアップロード」の2モードでアップロードを実行できます。
3. **実行状況表示** — 進捗バー・記事単位の結果ログ・中断ボタン。完了後は結果サマリと実行履歴(Run方向・Gitコミット情報含む)を表示します。

## アップロード(ローカル → Qiita)

ローカルの変更をQiitaへ反映できます。書き込みは明示的な操作と実行前確認を経た場合のみ行われ、自動同期はありません。

- **新規記事の登録** — 下記の作成規約で書いた記事を、**限定共有(非公開)**としてQiitaへ登録します(詳細は後述の「限定共有として登録される仕様について」)。
- **既存記事の本文更新** — 閲覧用Markdown(`{記事タイトル}.md`)をローカルで編集すると「ローカル変更あり」になり、アップロード候補になります(タイトル・タグの変更は同期対象外)。相対パス化された画像参照は、アップロード時に自動で元URLへ復元されます。
- **競合保護** — Qiita側とローカルの双方が変更された記事は「競合」となり、変更点全件アップロードと差分バックアップの両方から除外されます(選択+明示承認でのみ操作可能)。

### アップロードの手順

1. `backups/` 直下に記事フォルダを作成し、規約どおりのMarkdownを書く(下記)
2. ダッシュボードで「**一覧再取得**」→ 記事が「ローカル新規」として表示されることを確認
3. 記事にチェックを入れて「**選択をアップロード**」(または「変更点をアップロード」で候補全件)
4. 確認ダイアログで対象と警告(公開中記事への即時反映・競合・ローカル画像)を確認して「アップロードを実行」
5. 結果サマリで成功を確認。登録成功後、フォルダは既存記事と同じ構成(`{記事タイトル}_{記事ID}/`)へ自動変換され、状態は「最新」になり、以後は通常のバックアップ対象になります

### 限定共有として登録される仕様について

Qiita API v2には**「下書き」を作成する機能が存在しない**ため、本ツールは新規記事を**限定共有(private)**として登録することを「下書き相当」としています。次の点に注意してください。

- **Qiitaの「下書き一覧」(qiita.com/drafts)には表示されません。** 登録された記事は、自分の記事一覧に「限定共有」ラベル付きで表示され、結果サマリ・`meta.json` に記録される限定共有URL(`https://qiita.com/{user}/private/{記事ID}`)から直接開けます。
- **限定共有は「完全な非公開」ではありません。** URLを知っている人は誰でも閲覧できます(検索やタイムラインには載りません)。推敲中にURLを共有しなければ実質非公開ですが、機密情報を含む記事では留意してください。
- **公開はQiita上で行います**: 限定共有URLを開く → 「編集する」→ 公開範囲を「全体に公開」へ変更して投稿。ツールから記事を公開する機能は、誤公開防止のため意図的に実装していません。
- 既存記事の更新では公開範囲を変更しません(公開中の記事は公開のまま、更新内容が即時反映されます — 実行前確認で警告されます)。

### 新規記事の作成規約

`backups/` 直下に**任意名のフォルダ**を作り、その直下に **Markdownファイル(.md)を1つ**置きます。ファイル先頭にfrontmatterで `title`(必須)と `tags`(必須・1件以上)を記載します:

```markdown
---
title: 記事のタイトル
tags: [tag1, tag2]
---
ここから本文を書きます。
```

`tags` は `[a, b]` / `a b c`(スペース区切り)/ `- タグ名` の行区切り のいずれの書式でも指定できます(Qiitaのタグ名はスペースを含められないため、スペース区切りは複数タグとして解釈されます)。

一覧の再取得で「ローカル新規」として検出されます(規約不備の場合は理由付きでアップロード不可と表示)。

### 画像の自動アップロード(任意機能)

Qiita API v2 には画像をアップロードする手段がないため、本文が参照するローカル画像(`![図](images/a.png)` や `<img src="images/a.png">`)は、そのままではQiita上で表示されません。この任意機能を有効にすると、記事のアップロードの前に**ツールが開いたブラウザでQiitaのエディタ画面へ画像を投入**し、Qiitaが発行した画像URLで**送信する本文**の画像参照を置き換えます。

- **非公式な方法です**: Qiitaの画面を自動操作するため、画面が変わると予告なく動かなくなることがあります(その場合は処理を止め、手動手順を案内します)。Qiita利用規約に照らして問題と判断された場合にアカウントが凍結される可能性もあります。初回の有効化時に同意を求めます。
- **準備**: `npm install` で任意依存の `playwright-core` が入ります(ブラウザ本体は同梱しません)。Microsoft Edge または Google Chrome が必要です。導入後はサーバを再起動してください。
- **有効化**: ダッシュボードの「画像の自動アップロード(任意機能)」で有効にし、注意事項に同意します。ログイン状態を保存するかどうかも選べます(保存先は `.image-upload/browser-profile/`、Git管理外。画面から削除できます)。
- **使い方**: アップロードの実行前確認に画像の一覧(枚数・合計容量・送れない画像と理由)が表示されます。「ローカル画像をQiitaへアップロードしてから記事をアップロードする」にチェックして実行すると、ブラウザが開きます。Qiitaにログインしていなければ、**開いたブラウザでご自身でログイン**してください(ツールはID・パスワードを扱いません)。
- **ローカルのファイルは書き換えません**: 置き換えるのはQiitaへ送る本文だけで、閲覧用Markdownは相対参照のまま画像付きで閲覧できます。画像とURLの対応は `meta.json` の `uploadedImages`(新規記事は登録までフォルダ内の `.image-uploads.json`)に記録され、同じ内容の画像は二度送りません。
- **安全側に止まります**: 画像が1枚でも失敗した記事はアップロードしません。ログインが時間内に終わらない・ブラウザを閉じた・中断した場合は、記事を1件もアップロードしません。
- **作業用の下書き**: 画像の投入のため、Qiita上に作業用の下書きが1件残ります(次回も同じ下書きを使います)。不要になったらQiita上で削除してください。アップロードした画像は、URLを知っている人なら誰でも閲覧できます。

### アップロードが403で失敗する場合

Qiitaは**スコープ不足以外の理由でも403 Forbiddenを返す**ことがあります。失敗理由に表示されるQiitaの応答メッセージとあわせて、次を確認してください。

- **トークンのスコープ**: `write_qiita` が付いているか(バッジが「読み取りのみ」の場合は403の実績あり。トークンを確認・再発行して「接続設定」から再検証すると「未確認」にリセットされます)
- **タグ名・本文の不備**: 不正なタグ名などもQiitaは403で拒否します(400ではない点に注意)
- `.env` のトークンを直接書き換えた場合は**サーバの再起動**が必要です(起動時に読み込むため)

## バックアップの構成

```text
backups/
├── .git/                      # Run単位で自動コミット(ツール本体とは独立、コミット先は backup ブランチ固定)
├── index.json                 # 管理情報(状態・履歴)
└── {記事タイトル}_{記事ID}/
    ├── {記事タイトル}.md       # 画像参照を相対パス化した閲覧用Markdown
    ├── original.md            # 取得したままのMarkdown
    ├── meta.json              # 記事メタデータ(反応数・画像取得結果含む)
    └── images/                # 001_{元ファイル名}.png 形式
```

閲覧用MarkdownはVS Code等のMarkdownビューワでそのまま画像付きで閲覧できます。

## 開発

```powershell
npm test          # ユニット+統合テスト(vitest)
npm run typecheck # TypeScript型検査
npm run perf      # 性能検証(モック300記事×10画像、約15分)
node scripts/mock-qiita.mjs  # 開発用モックQiitaサーバ(トークン: mock-token)
```

モックサーバに対して動作させる場合は、環境変数 `QIITA_API_BASE_URL=http://127.0.0.1:4510/api/v2` を指定して起動します。

## セキュリティ

- トークンは `.env` とメモリ内のみに保持し、画面・ログには末尾4桁のマスク表示のみ
- `Authorization` ヘッダはQiita API(`qiita.com`)へのリクエストにのみ付与(画像取得には付けない)
- Qiitaへの書き込みは明示的なアップロード操作に限定(自動同期・定期実行なし)。記事の削除は行いません
- 新規記事は常に限定共有(非公開)で登録され、公開操作はQiita上でのみ行えます(誤公開の構造的防止)
- Webサーバは `127.0.0.1` のみで待ち受け。バックアップリポジトリへのリモート操作(push/pull)は実装していません
- `backup` ブランチはローカル専用です。バックアップリポジトリにpre-pushフックを自動設置し、手動を含む同ブランチのpushを拒否します(限定共有記事の誤公開防止)
- 画像の自動アップロード(任意機能)のブラウザセッションは、既定では保存せず実行ごとに破棄します。保存に同意した場合も `.image-upload/` (Git管理外)にのみ置き、ログには出力しません。ブラウザ操作部品にはアクセストークンを渡しません
